# Roadmap ระบบจัดการหอพักผ่าน LINE

ฉบับจัดทำใหม่ วันที่ 16 ตุลาคม 2569 (2026-10-16)  
โครงการ: Dormitory (Customer) / `dormitory-line`  
สถานะเอกสาร: แผนพัฒนาเพื่อทบทวนขอบเขตและใช้ติดตามงาน ยังไม่ใช่กำหนดส่งที่ตกลงกับลูกค้า

อ่านคู่กับ [Blueprint](BLUEPRINT.md) ซึ่งอธิบายโครงสร้างและกติกาของระบบ เอกสารนี้จัดลำดับการพัฒนาใหม่จากบรีฟและโค้ดที่ตรวจพบ โดยเก็บ [บรีฟเดิม](brief.pdf) ไว้เป็นหลักฐานต้นทาง

## 1. เป้าหมายและขอบเขต

พัฒนาระบบให้เจ้าของหอพักจัดการห้อง สัญญา มิเตอร์ บิล การรับชำระ เอกสาร และงานซ่อมจากเว็บ ผู้เช่าเปิดดูข้อมูลและทำรายการผ่าน LINE LIFF โดยเห็นเฉพาะข้อมูลตามสิทธิ์ของตนเอง

ขอบเขตตามบรีฟเดิมคือห้องพัก 18 ห้อง และร้านค้า 1 ยูนิต รวม 19 ยูนิต ห้องทั่วไปครบกำหนดสิ้นเดือน ห้อง 205 ครบกำหนดวันที่ 10 ข้อมูลนี้เป็นขอบเขตจากเอกสาร ไม่ใช่จำนวนห้องที่ตรวจพบในฐานข้อมูลจริง

MVP ครอบคลุม:

- เว็บเจ้าของ/แอดมิน: ห้อง สัญญา เชิญผู้เช่า มิเตอร์ บิล ตรวจชำระ แจ้งซ่อม และตั้งค่า
- LINE LIFF ผู้เช่า: ผูกบัญชี ดูบิลและมิเตอร์ อัปโหลดสลิป ดูเอกสาร และติดตามงานซ่อม
- งานเบื้องหลัง: คำนวณเงินบน Server ตรวจสิทธิ์ เก็บไฟล์แบบ Private แจ้งเตือน และทำงานตามเวลา

รายงาน Excel ใบเสร็จ PDF อัตโนมัติ กระบวนการคืนเงินประกัน หลายอาคาร PWA และ Payment Gateway อยู่ในแผนต่อยอดตามบรีฟ ไม่เพิ่มเป็นเงื่อนไขส่งมอบ MVP โดยอัตโนมัติ ส่วนการลงนามสัญญาอิเล็กทรอนิกส์ยังไม่มีขอบเขตพัฒนาที่ได้รับการยืนยัน

### Phase 0: ทำให้ตัวตนและสภาพแวดล้อมพร้อม

งาน:

- ยืนยันผู้ถือครองบัญชีบริการ แยกข้อมูลทดสอบออกจากข้อมูลจริง และจัดการ secret ตามสภาพแวดล้อม
- ตรวจ LINE ID token บน Server แล้วออก Supabase session ด้วยวิธีที่รองรับและทดสอบจริง ห้ามเชื่อ LINE User ID ที่ client ส่งมาเอง
- กำหนดวิธีเข้าใช้ของเจ้าของ/แอดมิน ป้องกันทั้งหน้าและทุก Server operation พร้อมทดสอบการออกจากระบบและ session หมดอายุ
- ตรวจ migration, RLS และ Storage policies ในฐานข้อมูลทดสอบจริง
- เตรียมขั้นตอน deployment ทดสอบ การติดตามข้อผิดพลาด และการย้อนกลับ ก่อนขออนุมัติใช้งาน Cloud

เกณฑ์จบ: ผู้เช่าเข้าสู่ระบบแล้วได้ตัวตนที่ RLS ใช้ได้จริง ผู้ไม่มีสิทธิ์เข้า Admin/เรียก API สำคัญไม่ได้ และมีหลักฐานจากสภาพแวดล้อมทดสอบ การมีหน้า LIFF หรือคำสั่ง build ผ่านอย่างเดียวยังไม่ผ่านเฟสนี้

### Phase 1: ห้อง สัญญา และผูกผู้เช่า

งาน:

- ทำ Rooms/Leases CRUD รองรับ `residential` และ `commercial` ตามข้อมูลที่ลูกค้ายืนยัน
- สร้างลิงก์/QR เชิญ เก็บเฉพาะ hash มีอายุ 7 วันตามบรีฟ ใช้ได้ครั้งเดียว และป้องกันการรับลิงก์พร้อมกัน
- ทำหน้ารับคำเชิญ ยืนยันชื่อ/เบอร์ และผูกบัญชีเข้ากับสัญญา
- จัดการผู้เช่าร่วมและผู้เช่าหลัก ปิดสัญญา ยกเลิกคำเชิญ และถอนสิทธิ์ทำรายการเมื่อย้ายออก
- ทำ Dashboard ผู้เช่าที่อ่านข้อมูลจริง พร้อมกรณีไม่มีห้อง/ไม่มีบิล

เกณฑ์จบ: สร้างห้องและสัญญาแล้วเชิญผู้เช่าจนเห็นข้อมูลได้ครบ ลิงก์หมดอายุ/ใช้ซ้ำถูกปฏิเสธ ผู้เช่าต่างห้องและคนละสัญญาในห้องเดียวกันเข้าถึงข้อมูลที่ไม่มีสิทธิ์ไม่ได้

### Phase 2: มิเตอร์และการออกบิล

งาน:

- ทำหน้าจดมิเตอร์หลายห้อง แนบรูป ตรวจเลขลดลงและการใช้ผิดปกติ
- ยืนยัน Q-03 ถึง Q-05 ก่อนกำหนดเดือนบิล ช่วงมิเตอร์ และกรณีพิเศษ
- ทำเอนจิน Server คำนวณค่าเช่า + ค่าน้ำเหมาจ่าย + หน่วยไฟ × อัตรา + รายการเพิ่ม − ส่วนลด
- เก็บอัตราและรายการของเดือนนั้นในบิล ไม่เปลี่ยนบิลเก่าเมื่อแก้ราคาสัญญา
- ออกบิลเองและเตรียมเรียกจาก Cron ป้องกันสร้างซ้ำ ล็อกบิลชำระแล้ว และเขียน audit log
- แสดงบิล/ประวัติ/กราฟจากข้อมูลจริงบน LIFF

เกณฑ์จบ: เจ้าของตรวจยอดเทียบตัวอย่างที่ตกลงแล้วตรงกัน ครอบคลุมสิ้นเดือน เดือนกุมภาพันธ์ รอบวันที่ 10 รอบร้านค้า และมิเตอร์ไม่ครบ งานซ้ำไม่สร้างบิลซ้ำหรือทำรายการเงินค้างครึ่งทาง

### Phase 3: รับชำระและตรวจสลิป

งาน:

- ยืนยัน Q-01/Q-06 แล้วทำ adapter เชื่อมผู้ให้บริการที่เลือก
- แสดง QR PromptPay ตามข้อมูลรับเงินที่ยืนยัน อัปโหลดสลิปเข้า Private Storage และตรวจไฟล์ฝั่ง Server
- เทียบยอด ผู้รับ วันเวลา และ reference จากผลตรวจจริง ป้องกันใช้สลิปซ้ำและการอนุมัติพร้อมกัน
- ทำคิวตรวจของแอดมิน อนุมัติ/ปฏิเสธพร้อมเหตุผลและ audit log
- กรณีตรวจไม่ได้ บริการล่ม หรือข้อมูลไม่ตรง ให้รอตรวจโดยแอดมิน ไม่เปลี่ยนเป็นชำระแล้ว
- แจ้งผลให้ผู้เช่าและแสดงสถานะล่าสุด ช่วงเริ่มใช้งานให้แอดมินยืนยันทุกรายการตามบรีฟ

เกณฑ์จบ: ออกบิล → อัปโหลด → ตรวจ → แอดมินยืนยัน → บิลชำระแล้ว ครบวงจร ทดสอบยอดผิด ผู้รับผิด สลิปซ้ำ provider timeout และการส่งซ้ำ โดยไม่เกิดการรับเงินซ้ำ

### Phase 4: เอกสารและงานซ่อม

งาน:

- อัปโหลดและเปิดสัญญา PDF ผ่านสิทธิ์ของสัญญาและ Signed URL
- แยกเอกสารห้องพัก/ร้านค้าตามเอกสารที่ลูกค้ายืนยัน ไม่ถือว่าการผูก LINE เท่ากับการลงนามสัญญา
- แจ้งซ่อมพร้อมหลายรูป หมวด ความเร่งด่วน และ timeline
- แอดมินรับงาน เปลี่ยนสถานะ แนบรูปผล และให้ผู้เช่ายืนยันปิดงาน
- ส่งแจ้งเตือนและตรวจการเข้าถึงรูป/เอกสารข้ามผู้เช่า

เกณฑ์จบ: ผู้เช่าดูเอกสารของตนเองและแจ้งซ่อมจนปิดงานได้ ไฟล์ Private เปิดโดยผู้ไม่มีสิทธิ์ไม่ได้ รองรับหลายรูปด้วยโครงสร้างที่พัฒนารองรับจริง

### Phase 5: Cron รวมระบบ และทดสอบรับมอบ

งาน:

- ทำ handler งานตามเวลาให้ครบ พร้อมการรันซ้ำ การกู้รอบที่พลาด และบันทึกผล
- ทำ LINE notifications จริง พร้อม deduplication/retry และการจัดการส่งไม่สำเร็จ
- ตรวจ RLS, Storage, API authorization, การเงิน และ session บนสภาพแวดล้อมทดสอบ
- UAT กับผู้เช่าจริง 2–3 ห้องตามแผนเดิม หลังลูกค้าเลือกผู้ร่วมทดสอบและอนุญาตใช้ข้อมูล
- ซ้อม backup/restore จัดทำคู่มือเจ้าของ/ผู้เช่า บันทึกข้อจำกัดและช่องทางดูแล

เกณฑ์จบ: มีหลักฐาน UAT ที่ลูกค้ายอมรับ ไม่มีประเด็นสิทธิ์/ยอดเงินค้างแก้ และมีแผนเปิดใช้กับผู้รับผิดชอบ การทดสอบในเครื่องหรือ deployment สำเร็จไม่ทดแทน UAT

### เปิดใช้งาน

- ขออนุมัติเผยแพร่/ปรับฐานข้อมูลจริงตามเป้าหมายที่ยืนยันก่อนดำเนินการ
- เดือนแรกเทียบยอดกับวิธีเดิมตามบรีฟ และทยอยเชิญผู้เช่า ไม่เปลี่ยนทั้งระบบโดยไม่มีข้อมูลตั้งต้นครบ
- ตรวจยอดเรียกเก็บ รับแล้ว ค้างชำระ สลิปซ้ำ และแจ้งเตือนตกหล่นทุกรอบ
- หลังใช้งาน 1–2 รอบบิลตามบรีฟ จึงทบทวนการอนุมัติอัตโนมัติร่วมกับลูกค้า ไม่เปิดเองจากการผ่าน unit test

### Phase 6: ต่อยอดหลังเปิดใช้

| ลำดับจากบรีฟ | งาน | เงื่อนไขก่อนเริ่ม |
|---|---|---|
| สูง | ใบเสร็จ PDF, รายงานรายรับ/Excel, ย้ายออก/คืนเงินประกัน | ข้อมูลรับชำระนิ่งและยืนยันรูปแบบเอกสาร/กติกาคืนเงิน |
| กลาง | ตรวจสภาพห้องพร้อมรูป, Rich Menu, สิทธิ์ Staff/ช่าง | ยืนยันผู้ใช้งานและสิทธิ์ของงานใหม่ |
| ต่ำ | วิเคราะห์ไฟผิดปกติ, หลายอาคาร, PWA, Payment Gateway | ประเมินความจำเป็นและอนุมัติขอบเขตเพิ่ม |

## 5. เวลาและการติดตาม

บรีฟเดิมประเมินสำหรับนักพัฒนา 1 คนเต็มเวลา: Phase 0 สัปดาห์ 1, Phase 1 สัปดาห์ 2–3, Phase 2 สัปดาห์ 4–5, Phase 3 สัปดาห์ 6–7, Phase 4 สัปดาห์ 8 และ Phase 5 สัปดาห์ 9–10 โดยแนะนำเผื่อประมาณสองเท่าหากทำนอกเวลา ตัวเลขนี้เป็นประมาณการเดิม ไม่ใช่ประมาณการใหม่จากงานที่เหลือ

ฉบับใหม่นี้ใช้เกณฑ์จบแต่ละเฟสแทนการกำหนดวันส่งที่ยังไม่ยืนยัน ต้องประเมินเวลาใหม่หลังตกลง Q-01 ถึง Q-08 ผู้พัฒนา และเวลาที่ลูกค้าพร้อมทดสอบ

ทุกงานควรบันทึก: ผู้รับผิดชอบ, สถานะ, ผลส่งมอบ, หลักฐานตรวจ, ปัญหาค้าง และวันที่ตรวจล่าสุด ใช้สถานะ “ยังไม่เริ่ม / กำลังทำ / รอข้อมูล / รอตรวจ / ผ่านเกณฑ์” การผ่านเกณฑ์ต้องอ้างหลักฐาน ไม่สรุปจากจำนวนไฟล์หรือจำนวนหน้าที่สร้าง

## 6. ความเสี่ยงและเกณฑ์ยอมรับ

| ความเสี่ยง | วิธีรับมือ/หลักฐานที่ต้องได้ |
|---|---|
| ข้อมูลข้ามผู้เช่าหรือคนละสัญญาในห้องเดียวกัน | ทดสอบตาราง ไฟล์ และ Server endpoints ทั้งก่อน/หลังย้ายออก |
| งวดค่าเช่าและมิเตอร์ไม่ตรง | ลูกค้ายืนยันตัวอย่างรอบบิลก่อนลงสูตร และตรวจยอดร่วมกัน |
| สลิปซ้ำ/อนุมัติซ้ำ | unique reference + transaction + ทดสอบ concurrent requests |
| Provider/LINE ส่งไม่สำเร็จ | คิว retry และบันทึกผล; งานเงินยังเสร็จได้โดยไม่สูญหลักฐาน |
| Cron รันซ้ำ/พลาด | deduplication, job log และการเรียกชดเชยที่ไม่สร้างยอดซ้ำ |
| ร่างเอกสารยังไม่ผ่านตรวจ | ให้ผู้รับผิดชอบยืนยันฉบับใช้งาน ไม่แปลงข้อความร่างเป็นกติกาบังคับอัตโนมัติ |

## 7. หลักฐานการตรวจในงานจัดทำเอกสารนี้
