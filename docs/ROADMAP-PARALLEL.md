# แผนทำงานคู่ขนาน: เส้นทาง A / B

จัดทำ: 17 ตุลาคม 2569 (2026-10-17)
โครงการ: Dormitory (Customer) / `dormitory-line`
สถานะ: แผนปฏิบัติการภายใน ใช้แบ่งงานให้ agent ทำพร้อมกัน ไม่ใช่กำหนดส่งที่ตกลงกับลูกค้า

อ่านคู่กับ [ROADMAP](ROADMAP.md) (ลำดับเฟสและเกณฑ์จบ) และ [BLUEPRINT](BLUEPRINT.md) (โครงสร้างและกติกา)
ไฟล์นี้ตอบเฉพาะ "จะแบ่งงานให้ 2 agent ทำพร้อมกันอย่างไรโดยไม่ชนกัน"

## 1. เหตุผลที่แบ่งเป็น 2 เส้นทาง

งานที่เหลือจาก ROADMAP แบ่งเป็น 3 กลุ่ม แต่กลุ่มหนึ่งทำพร้อมกันไม่ได้:

| กลุ่ม | สถานะ | เหตุผล |
|---|---|---|
| Phase 2 เอนจินคิดเงิน/บิล | **ห้ามเริ่ม** | รอ Q-03 ถึง Q-05 จากลูกค้า (วันออกบิลร้านค้า, ช่วงมิเตอร์, ส่วนลด/ค่าปรับ) ฝังสูตรเองคือแต่งข้อมูลให้ลูกค้า |
| Phase 3 รับชำระ/ตรวจสลิป | **ห้ามเริ่ม** | รอ Q-01 (SlipOK) และ Q-06 (บัญชีรับเงิน, ผู้อนุมัติ) |
| Phase 2a จดมิเตอร์ + Phase 4b งานซ่อม | ทำได้เลย | ไม่ฝังสูตรเงิน ไม่ต้องรู้คำตอบของลูกค้า |
| Phase 4a เอกสารสัญญา | ทำได้เลย | กลไกอัปโหลด/เปิดไฟล์ไม่ผูกกติกาเอกสาร (การแยกชนิดเอกสารรอ Q-07) |

เส้นทาง A รับชุดที่เป็น "ข้อมูลห้องที่มีรูปแนบ" (มิเตอร์ + ซ่อม)
เส้นทาง B รับชุดที่เป็น "ไฟล์เอกสารของสัญญา"
ทั้งสองเส้นทางแตะคนละตาราง คนละโฟลเดอร์ คนละไฟล์ migration

## 2. สิ่งที่หัวหน้าต้องทำเองก่อนเริ่มแบ่งงาน

ทั้ง 3 ข้อนี้เป็นไฟล์ร่วม ถ้าให้ agent แต่ละสร้างเองจะชนกัน หัวหน้าเป็นคนเขียน:

| ไฟล์ | หน้าที่ |
|---|---|
| `lib/storage.ts` | อัปโหลดไฟล์เข้า private bucket + ออก Signed URL ตามเวลาหมดอายุ ใช้ร่วมกันทั้ง 2 เส้นทาง |
| `supabase/tests/harness.mjs` | โค้ดเปิด PGlite + ใส่ schema จำลอง Supabase + รัน migration ทุกไฟล์ (แยกออกจาก `rls.test.mjs`) |
| `package.json` | เพิ่มสคริปต์ `test:path-a` / `test:path-b` ให้รันเทสต์ของแต่ละเส้นทาจาก harness |

สัญญาของ `lib/storage.ts` ที่ทั้ง 2 เส้นทางต้องใช้เหมือนกัน (ห้ามเปลี่ยน):

```
uploadPrivateFile(bucket, path, file: File): Promise<string>   // คืน path ที่บันทึกลง DB
signedUrl(bucket, path, seconds): Promise<string>
storagePath(bucket, ...parts): string                          // ต่อ path ด้วย /
```

## 3. เส้นทาง A — มิเตอร์ + งานซ่อม

### 3.1 ขอบเขตงาน

- ROADMAP Phase 2 ข้อแรก: หน้าจดมิเตอร์หลายห้อง แนบรูป ตรวจเลขลดลงและการใช้ผิดปกติ
- ROADMAP Phase 4 งานซ่อม: ผู้เช่าแจ้งพร้อมหลายรูป → แอดมินรับงาน/เปลี่ยนสถานะ/แนบรูปผล → ผู้เช่ายืนยันปิดงาน

### 3.2 ไฟล์ที่เส้นทาง A เป็นเจ้าของ (แตะได้เฉพาะเหล่านี้)

| ไฟล์ | สถานะ |
|---|---|
| `app/admin/meters/page.tsx` | เขียนใหม่จาก stub |
| `app/admin/meters/actions.ts` | สร้างใหม่ |
| `app/admin/meters/meter-form.tsx` | สร้างใหม่ |
| `app/liff/meters/page.tsx` | เขียนใหม่จาก stub |
| `app/admin/maintenance/page.tsx` | เขียนใหม่จาก stub |
| `app/admin/maintenance/actions.ts` | สร้างใหม่ |
| `app/liff/maintenance/page.tsx` | เขียนใหม่จาก stub |
| `supabase/migrations/20261018000000_phase2a_phase4b_meters_maintenance.sql` | สร้างใหม่ (ชื่อนี้เท่านั้น) |
| `supabase/tests/path-a.test.mjs` | สร้างใหม่ |

### 3.3 migration ที่อนุญาตให้เพิ่ม

- `meter_readings`: บังคับ `prev_value`/`curr_value` เป็นตัวเลข ไม่ติดลบ, เพิ่ม index `(room_id, period desc)` ถ้ายังไม่มี
- งานซ่อมหลายรูป: `maintenance_requests` ไม่มีที่เก็บรูป ต้องเพิ่มตารางหรือคอลัมน์ใหม่ (เช่น `maintenance_photos`) — **อย่า**แก้ `maintenance_updates` เดิม เพราะเส้นทาง B ไม่ได้แตะแต่ต้องไม่พังของเดิม
- ทุกอย่างที่เพิ่มต้องมี index/constraint ที่ทำให้ผู้เช่าคนอื่น (คนละสัญญา/คนละห้อง) อ่านไม่ได้ ผ่าน policy เดิมใน `storage_rls.sql` เป็นหลัก

### 3.4 เกณฑ์จบของเส้นทาง A

- แอดมินจดมิเตอร์หลายห้องได้ในหน้าเดียว พร้อมแนบรูป และระบบปฏิเสธเมื่อเลขปัจจุบันน้อยกว่าเลขก่อนหน้า
- ผู้เช่าเปิดหน้ามิเตอร์เห็นเฉพาะงวดที่อยู่ในช่วงสัญญาของตน
- ผู้เช่าแจ้งซ่อมพร้อมหลายรูปได้ ติดตามสถานะได้ และยืนยันปิดงานได้
- แอดมินเปลี่ยนสถานะงานและแนบรูปผลได้ โดยทุกการเปลี่ยนสถานะเขียน audit log
- `supabase/tests/path-a.test.mjs` พิสูจน์: ผู้เช่าคนอื่นอ่านไฟล์รูปไม่ได้, อัปโหลดเข้าห้องที่ไม่เช่าไม่ได้, จดมิเตอร์ซ้ำห้อง+งวดไม่ได้, ผู้เช่าปิดงานของห้องอื่นไม่ได้

## 4. เส้นทาง B — เอกสารสัญญา

### 4.1 ขอบเขตงาน

- ROADMAP Phase 4: อัปโหลดและเปิดสัญญา PDF ผ่านสิทธิ์ของสัญญาและ Signed URL
- หน้า LIFF ดูเอกสารของตนเองจากข้อมูลจริง
- ยัง**ไม่**ทำ: การแยกชนิดเอกสารห้องพัก/ร้านค้าตามที่ลูกค้ายืนยัน (รอ Q-07) ให้ใช้ค่า `type` แบบข้อความอิสระและเขียนกำกับว่ารอการยืนยัน

### 4.2 ไฟล์ที่เส้นทาง B เป็นเจ้าของ (แตะได้เฉพาะเหล่านี้)

| ไฟล์ | สถานะ |
|---|---|
| `app/admin/documents/page.tsx` | สร้างใหม่ |
| `app/admin/documents/actions.ts` | สร้างใหม่ |
| `app/liff/documents/page.tsx` | เขียนใหม่จาก stub |
| `supabase/migrations/20261018000001_phase4a_documents.sql` | สร้างใหม่ (ชื่อนี้เท่านั้น) |
| `supabase/tests/path-b.test.mjs` | สร้างใหม่ |

### 4.3 migration ที่อนุญาตให้เพิ่ม

- `documents`: เพิ่ม `uploaded_by` (อ้าง `profiles`), `created_at` default มีอยู่แล้ว, และดัชนี `(lease_id, created_at desc)`
- path ของไฟล์ต้องเป็น `documents/<lease_id>/<file>` ให้ตรงกับ policy `tenant_documents_select` ที่มีอยู่แล้ว
- ผู้เช่าอัปโหลดเอกสารเองไม่ได้ (policy เดิมให้ staff เท่านั้น) — ห้ามให้สิทธิ์ใหม่โดยไม่มีเหตุผลที่บันทึกไว้

### 4.4 เกณฑ์จบของเส้นทาง B

- แอดมินอัปโหลด PDF/รูปสัญญาเข้าห้องใดห้องหนึ่งได้ ผูกกับสัญญาห้องนั้น
- ผู้เช่าเห็นเฉพาะเอกสารของสัญญาตน และเปิดไฟล์ผ่าน Signed URL ที่อายุสั้น
- ผู้เช่าคนอื่น (คนละห้อง/คนละสัญญาในห้องเดียวกัน) เห็น 0 รายการ และเรียก Signed URL ของผู้อื่นไม่ได้
- ผู้เช่าย้ายออกแล้วเปิดเอกสารเดิมไม่ได้
- `supabase/tests/path-b.test.mjs` พิสูจน์ 4 ข้อข้างบนบน PGlite

## 6. กติกาที่บังคับกับทั้งสองเส้นทาง

1. ห้าม `git commit`, `git push`, `git add` — หัวหน้าเป็นคน commit และรัน `kb-review`
2. ห้ามรัน `npm run build` / `npm run dev` — จะชนกันที่โฟลเดอร์ `.next`; ให้หัวหน้ารัน
3. ห้ามเพิ่ม dependency ใหม่ใน `package.json`
4. ห้ามอ่านหรือเขียนค่าใน `.env.local` และห้ามพิมพ์ secret ออกมา
5. ห้ามแก้สูตรเงิน รอบบิล หรือกติกาการคิดค่าใช้จ่ายใด ๆ (รอ Q-03 ถึง Q-05)
6. ทุก server action ฝั่งแอดมินต้องเรียก `requireStaff` จาก `@/lib/phase1` ก่อนเขียนข้อมูล
7. ทุกการเปลี่ยนแปลงที่มีผลต่อสิทธิ์หรือสถานะเอกสาร ต้องเขียน audit log ผ่าน `audit()` ใน `@/lib/phase1`
8. คอมเมนต์และข้อความใน UI เป็นภาษาไทย ให้ตรงกับสไตล์เดิมในโปรเจกต์
9. ตารางเงินเป็น `numeric(12,2)` — ห้ามแปลงเป็น float ในการคำนวณ
10. ห้ามอ้างว่างานเสร็จโดยไม่มีหลักฐาน: ถ้าไม่ได้รันอะไรได้ ให้เขียนว่า "ไม่ได้รัน" ลงในรายงาน

---

## 7. ขั้นตอนส่งงานและรวบรวม

1. หัวหน้า commit งานที่ค้างอยู่ให้สะอาดก่อน เพื่อไม่ให้งาน agent ปนกับงานค้าง
2. ส่ง prompt ของแต่ละเส้นทาง (ข้อ 8) ให้ agent ทำพร้อมกัน
3. รับรายงานกลับมา แล้วหัวหน้าเป็นคนแก้ไฟล์ร่วมที่ agent ขอ
4. หัวหน้ารันเอง: `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`
5. commit แยกตามเส้นทาง (commit ละเส้นทาง ไม่ปนกัน)
6. รัน `kb-review -by <agent ที่เขียน>` — FAIL ต้องแก้และรีวิวใหม่ จน PASS
7. `git push` เป็นระดับ 3 ต้องขออนุมัติผู้ใช้ก่อนทุกครั้ง

## 8. Prompt สำหรับ agent แต่ละเส้นทาง

ใช้ข้อความนี้แทนที่คำสั่งงานทั่วไป เปลี่ยนเฉพาะส่วนในวงเล็บเหลี่ยม

```
คุณทำงานในโปรเจกต์ Z:\projects\Dormitory (Customer)\dormitory-line

อ่านก่อน: docs/ROADMAP-PARALLEL.md ข้อ [A หรือ B] และไฟล์ที่ระบุในนั้น
ห้ามอ่านและแก้ไฟล์นอกเฉพาะที่ระบุในข้อ [x.y.2] เด็ดขาด
ห้ามแก้ไฟล์ที่ระบุในข้อ 5
ห้าม commit / push / npm install / npm run build / npm run dev
ใช้เฉพาะ lib/storage.ts, lib/phase1.ts, app/components/ui.tsx ที่มีอยู่แล้ว ห้ามสร้างใหม่

งาน: [งานตามข้อ 3.1 หรือ 4.1]
เทสต์: เขียน supabase/tests/path-[a หรือ b].test.mjs โดยใช้ harness ที่มีอยู่แล้ว

รายงานกลับมาในรูปแบบนี้เท่านั้น
- ไฟล์ที่แก้/สร้าง พร้อมบรรทัดที่สำคัญ
- migration ที่เพิ่ม: ตาราง/คอลัมน์/policy ที่เพิ่ม และผลของ policy เดิมที่กระทบ
- รันอะไรได้บ้าง (พิมพ์คำสั่งและผล) และรันอะไรไม่ได้เพราะถูกห้าม
- สิ่งที่ยังไม่ทำและเหตุผล
- ไฟล์ร่วมที่ต้องการให้หัวหน้าแก้ (ถ้ามี)
ห้ามสรุปว่างานเสร็จถ้ายังไม่มีหลักฐานรัน
```
