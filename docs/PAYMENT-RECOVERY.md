# เก็บสลิปและแจ้งเตือนแอดมิน

ตามคำสั่งผู้ใช้วันที่ 17 ตุลาคม 2569: เก็บรายการสลิปและ log ใน Database ส่วนรูปอยู่ใน Private Storage แล้วแจ้งเตือนบนเว็บแอดมินให้ตรวจสอบ

## การทำงาน

1. อัปโหลดรูปเข้า private bucket `slips` แล้วสร้าง `payments` พร้อม `submitted_by` และตำแหน่งไฟล์
2. Trigger บันทึก `payment.upload.received` ใน `audit_logs` และสร้าง `notifications` ช่องทาง `web` ให้ owner/admin ใน transaction เดียวกับรายการสลิป
3. เก็บผลตรวจใน `payment_verifications` พร้อม reference ที่ป้องกันใช้สลิปซ้ำ ไม่ลบ log หรือรูปเมื่ออนุมัติ/ปฏิเสธ
4. RPC `finalize_invoice_payment_verification` อ่านผลที่เก็บไว้แล้วเปลี่ยนสถานะ payment/บิลและบันทึก audit พร้อมกัน หากล้มเหลว รายการและรูปเดิมยังอยู่
5. แอดมินเห็นแจ้งเตือนทุกหน้า พร้อมห้อง/งวดและลิงก์เข้าคิวตรวจ ระบบตรวจคิวทุก 15 วินาทีเมื่อหน้าเว็บเปิดอยู่ และตรวจอีกครั้งเมื่อกลับมาที่หน้า
6. หากรายการค้าง `uploaded` แอดมินกด **นำผลตรวจเดิมกลับเข้าคิว** เพื่อใช้ log เดิม ไม่เรียกผู้ให้บริการซ้ำ ไม่ต้องให้ผู้เช่าโอนเงินหรือส่งสลิปใหม่ จากนั้นตรวจรูปและอนุมัติแยกตามปกติ

แจ้งเตือนแสดงจำนวนรายการที่ยังต้องตรวจ ไม่ใช่จำนวนข้อความที่ยังไม่อ่าน เมื่ออนุมัติหรือปฏิเสธ รายการจะออกจากแจ้งเตือนรอบถัดไป ส่วน log ยังคงอยู่ใน Database

## ขอบเขตการกู้คืนและสิทธิ์

- RPC รับเฉพาะ payment ID กับ actor ที่ server ตรวจแล้ว ไม่รับสถานะหรือยอดจาก browser; ถอนสิทธิ์เรียกจาก `PUBLIC`, `anon`, `authenticated` และให้เฉพาะ `service_role`
- Server action ตรวจ session และ role owner/admin ก่อนใช้ service key; endpoint แจ้งเตือนตรวจสิทธิ์ทุกครั้งและไม่ cache ข้อมูลร่วมระหว่างผู้ใช้
- ใช้ได้เมื่อมีผลตรวจเดิมของรายการนั้นเพียงหนึ่งรายการที่อ่านได้ ผล `slipok_passed` ต้องมี reference ตรงกันและยอดเต็มบิลตรงกัน
- หากไม่มี log, log กำกวม/ผิดรูปแบบ, reference/ยอดไม่ตรง หรือรายการถูกปฏิเสธ/อนุมัติแล้ว RPC จะไม่เปลี่ยนเป็นผลผ่าน ต้องตรวจรายการเดิมเพิ่มเติม ไม่ใช้การส่งสลิปซ้ำเป็นทางกู้คืน
- ไม่เปลี่ยน `mismatch` หรือ `slipok_failed` ให้ตรวจผ่าน และไม่อนุมัติเป็น paid โดยอัตโนมัติ
- หากผลตอบกลับ INSERT ขาดหาย จะตรวจ receipt ตาม path ก่อน หากยังยืนยันไม่ได้ จะเก็บไฟล์ไว้แทนการลบไฟล์ที่อาจมีรายการอ้างถึงแล้ว

## Migration และการตรวจสอบ

ไฟล์ใหม่: `supabase/migrations/20261018000006_payment_logs_and_recovery.sql` สร้างด้วย CLI แล้วเรียงต่อท้าย migration ที่มีอยู่ โดยไม่แก้ไฟล์เก่าที่ถูก push แล้ว

ทดสอบ local ด้วย `npm run test:payments` และ `npm test` ครอบคลุม route จริงร่วมกับ PGlite, INSERT สำเร็จแต่ response หาย, finalization ล้มแล้วกู้คืนโดยไม่อัปโหลดซ้ำ, reference เดิมยังอยู่, ข้อจำกัดสิทธิ์, audit rollback, notification transaction และ endpoint แจ้งเตือน

ยังไม่ได้ apply migration, push หรือ deploy ในงานนี้ การใช้บน Cloud ต้องตรวจ applied migration ledger และอนุมัติเป้าหมายก่อนนำ migration ที่ยังขาดไปใช้ตามลำดับ การทดสอบในเครื่องไม่แทน live-provider/Storage UAT
